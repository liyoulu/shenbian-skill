# 检测器（-d）与标记点（-l）选型，及 3d68 修复

> 依据：2026-09-30 在 <DFL_ROOT> 上实测（8 个标记点 × 5 张多尺度输入、700 张现成脸集分档、平面内旋转扫描、
> 与 DFL 规范 3D 模板比对）。所有结论都可复跑，脚本见 `tools/marker_probe/`。
> 术语纠错：**S3FD 是检测器（`-d`），不是标记点**；标记点是 `-l`，v4.0.x 实际有 **8 个**（文档旧版写"5 个"已过时）。

## 0. 切脸选型速查（先看这个；全部依据见下文 §一～§八）

**三句话记住**：① 判据是"人脸在输入图里占多大比例"，**不是**"素材是视频还是图片"；② 检测器只管框（+5 点），68 点标记点是 `-l` 的另一环；③ 训练素材要"齐"、临时 merge 要"全"。

### 0.1 检测器 `-d`：按素材形态选

| 素材形态 | 选它 | 依据 |
|---|---|---|
| 整帧视频、远中景为主、占比稳定（最常见） | `TinyMog`（作者默认，最省 0.5s/2.7MB）或 `RetinaFace_10g` | WIDER 系训练分布正好匹配"整帧 + 中小脸" |
| **近景特写多 / 近远景混剪（跨尺度）** | **`YoloV11nFace`** | 与 V8 同速档、框一致性 0.96；真实片源基准 16/20 正常（V8 只有 1/20，见 §8.7）。V8 在 320–1280 全 input_size 的 30/30 只成立于对齐头像素材，**真实片源上会整段失效** |
| 已裁人脸图二次处理 | **`YoloV11nFace`**（或 YoloV8Face，先本地验证）；若用 RetinaFace 系必须 `--input-size 384` | 大脸占比超出 WIDER 系分布：640 时只 10/30，384 时 30/30 |
| 极限小脸（远景/人群） | `RetinaFace_10g`（**= DamoFD，同一 MD5**），保持 `--input-size 640` | 小脸极限 28px 最好、框一致性 0.97 |
| 要复现老 DFL 的结果 | `S3FD` | 精度 0.87 / 24.4s，只值"可比" |
| 极省算力且素材确定没有近景 | `TinyMog` | 唯一优势是 2.7MB / 0.5s |
| **别用** | `MogFace`（140s）、`ULFD`（框约定 IoU 0.46）、`LightweightFD`（非等比 resize，IoU 0.26）、`CenterFace`（CPU device 加载失败） | |

### 0.2 标记器 `-l`：按用途选

| 用途 | 选它 |
|---|---|
| **默认（绝大多数素材）** | **`insightface-2d106det`** — 取景最稳、106 点最密、5–12 ms、免补丁；真实片源残差 0.059（§九） |
| **省算力首选（超长片 / 几万帧）** | **`PFLD`** — **1 ms/帧**（比 FAN 快约 140×）、真实片源残差 0.055、取景抖动最小（§九） |
| 侧脸/大角度/whole_face/head、关键素材 | `3DFAN-4` — 侧脸四档全优（0.041–0.047）、极端侧脸最好（0.413）；代价 140 ms/帧 + 91MB×2 权重 |
| 要真 3D（z 坐标） | `insightface-3d68` — 已修三处（§五）；真实片源残差 0.050 最低、41–113 ms；需自己取 z + 一次 3D 相似定标 |
| 需要恒定 256 输出 | `Google-mediapipe`（自带一套取景且已知左偏，别与别家混用） |
| **不用** | `OpenSeeFace`（0.170 最差，解码漏 logit）、`MobileFaceNet`（0.110、取景偏差大）、`2DFAN-4`（与 3DFAN 同级但侧脸弱） |

### 0.3 成套命令

```powershell
Set-Location <DFL_ROOT>   # 你的深变安装目录
# 常规整片（默认就这套）
.\python\python.exe Extractor\Extractor.py -i <视频> -o <绝对路径>\aligned -d YoloV11nFace -l insightface-2d106det -t whole_face
# 侧脸/大角度/关键素材
.\python\python.exe Extractor\Extractor.py -i <视频> -o <绝对路径>\aligned -d YoloV11nFace -l 3DFAN-4 -t whole_face -a 0,90,180,270
# 远景小脸 / 已裁大脸图（-d 换成 RetinaFace_10g，input-size 按素材：小脸 640 / 大脸 384）
.\python\python.exe Extractor\Extractor.py -i <视频> -o <绝对路径>\aligned -d RetinaFace_10g -l 3DFAN-4 -t whole_face
```
训练素材 vs 临时 merge 的标准差异（清洗、`-s`、覆盖、`-a` 等）见 [merge-workflow.md](merge-workflow.md) 的「切脸标准对照」节。

### 0.4 动手前先问用户这 5 件事

1. 素材是**整帧视频**还是**已裁脸图**？（定检测器）
2. **人脸占比跨不跨尺度**、有没有近景特写？（决定要不要 Yolo）
3. 这批切脸是**喂训练**还是**给已有模型临时 merge**？（定清洗、`-s`、覆盖）
4. 模型的 **face_type 是什么**？（`-t` 必须一致，硬约束）
5. **侧脸/倒置多不多**？（定 `-a` 与 3DFAN-4）

### 0.5 切完必做自检

**点云宽 / 人脸框宽 = 0.8–1.0**（<0.5 就是标记点到像素的换算坏了，典型症状是"一部分脸正常、一部分不可用"）；抽检取景中心是否一致。
自检与复跑脚本见 §七（`tools/marker_probe/`）。

## 一、选型结论（照这个用）

| 优先级 | 组合 | 用在什么时候 |
|---|---|---|
| **P0 默认** | `-d YoloV11nFace -l insightface-2d106det` | 检测器取真实片源基准里正常的档（V8 会整段失效，§8.7）；标记点取景最稳、106 点最密 |
| **P0′ 省算力（超长片）** | `-l PFLD` | 1 ms/帧（比 FAN 快 ~140×）、真实片源残差 0.055、取景抖动最小（§九） |
| **P1 侧脸/大角度/关键素材** | `-l 3DFAN-4`（可配 `-a 0,90,180,270`） | 侧脸四档全优（0.041–0.047）、极端侧脸最好；代价 140 ms/帧 + 两个 FAN 权重各 91MB |
| **P2 要真 3D（z）** | `-l insightface-3d68` | 唯一有 z、与规范 3D 模板拟合残差 3.4% 脸宽；真实片源残差 0.050 最低；依赖 §五 本地补丁 |
| **P3 定尺输出** | `-l Google-mediapipe`（FaceMesh 468→68） | 需要恒定 256 输出时；自带一套取景（76% vs 其余 63%）且已知左偏，别混用 |
| **P4 不用** | `-l 2DFAN-4`、`-l MobileFaceNet`、`-l OpenSeeFace` | 同级更慢/取景偏差大/0.170 最差 + 2–4% 系统性平移 |
| 触发式替换 | 侧脸多 → 3DFAN-4；帧数极多 → PFLD；要 3D → 3d68 | 这是仅有的三种值得从默认换掉的理由 |

**同一部片（乃至同一批预训练集）只固定一套 `-d`/`-l`**：不同标记点的取景比例和输出尺寸不同（实测同一张脸 2d106 出 762px、3d68 出 722px、mediapipe 恒 256），混用会污染脸集。

## 二、8 个标记点实测对照（Extractor 路径，5 张 96–768px + 20° 旋转件，检测器 S3FD）

| `-l` 标记点 | 点云/人脸框比 | 成品人脸占比 | 人脸中心 | 输出尺寸 | 5 张耗时 |
|---|---|---|---|---|---|
| insightface-2d106det | 0.82 | 64% | (0.41,0.50) ±0.002 | 94–762 | 5.9s |
| 2DFAN-4 | 0.81 | 67% | (0.41,0.50) ±0.003 | 92–748 | 6.7s |
| 3DFAN-4 | 0.87 | 63% | (0.42,0.50) ±0.004 | 94–786 | 5.8s |
| insightface-3d68（修复后） | 0.81 | 68% | (0.41,0.51) ±0.002 | 90–722 | 5.8s |
| Google-mediapipe | 0.78 | 76% | (0.42,0.50) ±0.005 | 256–256 | 7.5s |
| OpenSeeFace | 0.87 | 62% | (0.40,0.47) ±0.005 | 94–772 | 4.6s |
| PFLD | 0.86 | 64% | (0.41,0.50) ±0.002 | 94–770 | 4.7s |
| MobileFaceNet | 0.91 | 58% | (0.42,0.47) ±0.001 | 98–788 | 5.4s |

**点云/人脸框比 = 标记点云的横向跨度 ÷ 检测框宽度，正常应落在 0.8–1.0**。这是判断"标记点到像素的换算有没有坏"最快的自检指标：
低于 0.5 基本就是坏了（3d68 坏掉时是 0.17，症状正是"一部分脸正常、一部分不可用"）。

### 精度与鲁棒性（越小越准/越稳）

| 标记点 | 形状共识残差 RMS/IOD | 平面内旋转自洽（+15°…+45°） |
|---|---|---|
| **3DFAN-4** | **0.0533** | 0.030–0.036 |
| PFLD | 0.0672 | 未测 |
| insightface-2d106det | 0.0787 | 0.008–0.027 |
| 2DFAN-4 | 0.0801 | 0.031–0.038 |
| insightface-3d68 | 0.0811 | **0.004–0.011** |
| MobileFaceNet | 0.0971 | 未测 |
| Google-mediapipe | 0.1094 | 未测 |
| OpenSeeFace | 0.1532 | 未测 |

- **形状共识残差**：留一法，取"其余标记点逐点中位数"作共识，做相似变换对齐后算 RMS，除以双眼间距。没有人工真值时的精度代理。
- **平面内旋转自洽**：同一张脸旋转后把点反向旋回、相似对齐再比，衡量姿态变化下的稳定性。

### 侧脸（平面外）分档（现成脸集 700 张抽样，按对称性指标 asym 分档，每档 10 张）

asym = |d(鼻梁27, 左颌0) − d(鼻梁27, 右颌16)| / 两者之和；正脸≈0，侧脸→大（是代理指标，不是真 yaw）。

| asym 档 | 2d106 | 2DFAN-4 | 3DFAN-4 | 3d68 |
|---|---|---|---|---|
| 正脸 <0.04 | 0.0809 | 0.0517 | **0.0469** | 0.0512 |
| 轻侧 0.04–0.10 | 0.0689 | 0.0514 | **0.0409** | 0.0475 |
| 中侧 0.10–0.20 | 0.0715 | 0.0540 | **0.0434** | 0.0516 |
| 大侧 >0.20（极端） | 0.4638 | 0.5017 | **0.4131** | 0.6438 |

**3DFAN-4 在每一档都是最好或并列最好，极端侧脸更明显**——3D-FAN 的平面外优势实测成立。
极端侧脸档四个标记点全部 >0.4（都不可信），此时应靠检测器召回 + 多角度检测 `-a 0,90,180,270`，而不是换标记点。

## 三、3D 相关（问"哪个 3D 更准"时看这节）

| 模型 | ONNX 输出 | 有 3D 坐标吗 |
|---|---|---|
| 2DFAN-4 / **3DFAN-4** | `[1, 68, 64, 64]` 纯 2D 热图 | **没有** |
| insightface-3d68 | `[1, 3309]` = 1103×3，**末 68 行**才是 x/y/z | 有（前 68 行恒为 0） |

- **3DFAN 的"3D"指训练用了 3D 标注**（Deng 3D-FAN），收益体现在 2D 点在姿态下更准；封装 `FAN.extract()` 只 argmax 解 x/y，**拿不到 z**。
- **3d68 的 z 实测可信**：与 DFL 规范模板 `landmarks_68_3D` 做 3D 相似拟合（用 17–67 号点），残差 RMS **4.98 模板单位 = 脸宽 3.4%**，x/y/z 通道相关 **0.996 / 0.997 / 0.968**；鼻尖 z −29.7（模板 −37.0）、眼角 6.9/5.3（模板 7.0/4.9）逐一吻合。它的自身坐标系与模板差 **28°**，要用 z 必须先做一次 3D 相似定标。
- 但**仓库目前把 z 丢掉了**：`Extractor/Extractor.py` 取 `pred[:, 0:2]`、`MergeStudio/.../pipeline.py` 取 `[-68:, :2]`。要 z 得自己改。
- DFL 的头姿估计**不依赖标记器的 z**：`LandmarksProcessor.estimate_pitch_yaw_roll` 用固定模板 `landmarks_68_3D` + 2D 点做 solvePnP；作者在 `estimate_averaged_yaw` 上方注明 "Works much better than solvePnP if landmarks from 3DFAN"，即官方偏好 3DFAN 的 2D 点。

**结论**：要"最准的 2D 点"→ 3DFAN-4；要"真的 3D 坐标"→ 3d68（唯一有 z，需定标、需改代码、2D 精度低一档 0.081 vs 0.053）。

## 四、OpenSeeFace 的已知缺陷（未修前别用）

- 坐标空间与轴向都对（用封装自己的解码与 PFLD 前 48 点做相似变换对齐，RMS 4.84px/224），**但偏移热图解码漏了上游的 logit 变换**：上游是 `res*logit_arr(p)`，本地封装写成 `223.0*off_x/16.0+0.5`，实测偏移比上游大 +4px（中位）～+9px（极端），约合裁剪边长的 2–4%。成品上量到的取景中心 (0.40,0.47) 比其它标记点偏约 3%，与之吻合。
- 且**没有置信度门控**：`OpenSeeFace.py` 里 `if mean_conf < 5.0: pass` 是空分支，非人脸裁剪不会被拒。
- 修法：把 `OpenSeeFace.py` 的偏移解码改回 `res*logit_arr(p)` 并加置信度门控；不想修就直接用 PFLD（同为轻量，取景更稳）。

## 五、insightface-3d68 的三处 bug 与本地修复（2026-09-30）

| # | 位置 | 问题 | 修复 |
|---|---|---|---|
| 1 | `modelhub/onnx/InsightFace3D68/InsightFace3D68.py` | 输入用 `to_ufloat32()` 除成 [0,1]，而模型（insightface 惯例）要 **0–255** 原始像素 → 输出退化，点云只有真实人脸的 0.17 倍 | 改 `as_float32()`（与同目录 2d106 封装一致） |
| 2 | `MergeStudio/core/detector/pipeline.py` | 对一维 `(3309,)` 输出做 `landmark_results[0]` 会取到 0 维标量 → `pts.shape[0]` 抛 IndexError → 被 `except: continue` 吞掉，**每张脸静默跳过** | 增加一维输出分支：`reshape(-1,3)[-68:]` 并换算成 face_img 像素坐标 |
| 3 | 同上（注释） | 原注释写 "first 68 are standard landmarks"，与实际相反（**标记点在最后 68 行，前 68 行为 0**） | 注释改正 |

- **备份**：`<DFL_ROOT>\_fix_backup_20260930\`（含相对路径）。**回滚**=把两个文件复制回去。
- **副作用**：改的是官方封装源码，**仓库升级会覆盖**。识别症状：3d68 的点云/框比掉回 ~0.2，或 MergeStudio 里 3d68 检出 0 张脸 → 补丁被覆盖了。
- **改完必须重启 GUI/MergeStudio**（Python 已导入的旧模块不会热更新）。
- **修复前后**：Extractor 路径 云/框比 0.17 → 0.81、人脸中心 (0.50,0.44)±0.016 → (0.41,0.51)±0.002；MergeStudio 路径 0 张脸 → 1 张脸（68×2 点、云/框比 0.87、对齐成品 256×256）。其余 7 个标记点各项数字无变化（无回归）。

## 六、做自定义分析时的额外坑

- **2d106 的原始输出是 106 点布局**，必须先经 `Extractor.landmark106to68`（作者标注"这个我能确保是包对的"）映射后才能当 68 点用；直接对原始输出用 68 点索引（如取 36:48 当双眼）会得到完全错误的结论。
- **各封装预处理各自为政**：2d106 喂 `swap_ch()` 的 **RGB 0–255**；FAN / FaceMesh 喂 **BGR [0,1]**（`to_ufloat32()`）；3d68 修复后喂 **BGR 0–255**。所以跨标记点的 landmarks 不要横着比，只在自己那一套里用。
- **FAN 是 64×64 热图 argmax**：在 256 输入下格点 4px（≈1.6%），有半格采样偏差，做亚像素需求时要自己插值。
- **非 ASCII 路径**：`cv2.imread` 在 Windows 上会读不了中文/表情符文件名（返回 None），要用 `np.fromfile` + `cv2.imdecode`。
- **测指标时先过检查**：比对不同标记点前，先确认各自的点云/框比都在 0.8–1.0，否则测的是"换算 bug"而不是"模型差异"。

## 八、人脸检测器（-d）选型与实测（2026-09-30）

用例 43 个 = 分辨率梯度 7 档（768→96px，人脸框有精确真值）+ 小脸大图 4 档（120/80/56/40px 人脸贴进 768 画布）+ 旋转 2 档（±20/25°）+ 真实脸集 30 张。CPU ORT，同机同批。

| 检测器 | 跨尺度框一致 IoU | 小脸大图 30–120px | 真实脸集 30 张 | 与共识框 IoU | 43 例耗时 | 定位 |
|---|---|---|---|---|---|---|
| **YoloV11nFace** | 0.72 | 4/4 | 30/30 | **0.96** | 1.3s | 综合首选 |
| **YoloV8Face** | 0.71 | 4/4 | 30/30 | 0.95 | 1.3s | 综合首选（默认 threshold 0.3 / min_face 8，灵敏） |
| **S3FD** | 0.69 | 2/4 | 30/30 | 0.87 | **24.4s** | 老 DFL 同款基准；比 Yolo 慢约 20×，默认 threshold 0.95 保守 |
| BlazeFace | **0.99** | **1/4** | 30/30 | 0.71 | **0.2s** | 最快（约 60× 于 S3FD），但**只见近景大脸** |
| MTCNN | 0.71 | 4/4 | 29/30 | 0.94 | 2.5s | 可用 |
| YoloV5Face | 0.77 | 4/4 | 30/30 | 0.86 | 2.4s | 可用 |
| MogFace | 0.70 | 4/4 | 30/30 | 0.93 | **140.3s** | 精度好但慢到不可用 |
| RetinaFace_10g / _500m | 0.72 / 0.70 | 4/4 | **10/30** | 0.97 | 2.9s / 0.5s | WIDER 系，小脸强；大脸漏（见结论 1） |
| DamoFD | 0.72 | 4/4 | **10/30** | 0.97 | 2.9s | 同上 |
| TinyMog | 0.67 | 4/4 | **11/30** | 0.94 | 0.5s | 同上，且分辨率极限最差（128px 图才检出） |

| CenterFace | — | — | — | — | — | CPU device 加载失败（需 GPU device） |
| FastFaceAlign | — | — | — | — | — | MergeStudio 工厂未注册（Extractor CLI 有，未测） |

**结论：检测器不是排名，是匹配。**

1. **近景 / 已裁大脸**（切脸常见素材）→ `YoloV11nFace`（V8 在对齐头像上最强，但真实片源会整段失效，见 §8.7）；要和老 DFL 基准可比才用 `S3FD`（慢约 20×）；`BlazeFace` 只在"脸占画面很大 + 要极速"时用。
2. **远景 / 小脸多** → `RetinaFace_10g` / `DamoFD` / `TinyMog`（WIDER 系）。但它们**在脸占画面一半以上的图上会漏检**：实测真实脸集（已裁大脸）默认 `input_size=640` 只检出 10/30，把 `--input-size 384` 一调全部检出 → 用它们必须按素材调 input_size。
3. **旋转不是区分点**：±20/25° 全部 2/2 检出；侧脸/倒置仍靠 `-a 0,90,180,270`。
4. 表里两个 IoU 都不是绝对精度（无人工标注真值）：第一列是"与 BlazeFace 框约定的一致度 + 跨尺度稳定性"，第五列是"与全体检测器共识框的一致度"。
5. 默认阈值决定召回倾向：S3FD `threshold=0.95, min_face_size=40`（保守）、YoloV8Face `0.3 / 8`（灵敏）、RetinaFace `det_thresh=0.5`。

### 8.4 首选之争：YoloV8Face vs TinyMog（input_size 敏感度实测）

30 张**已裁人脸图**（人脸约占画面 60%），只改 `--input-size`（one_stage）：

| 检测器 | 320 | 384 | 480 | **640（默认）** | 768 | 960 | 1280 |
|---|---|---|---|---|---|---|---|
| **YoloV8Face** | **30/30** | **30/30** | **30/30** | **30/30** | **30/30** | **30/30** | **30/30** |
| RetinaFace_10g | 30/30 | 30/30 | 30/30 | 10/30 | 0/30 | 0/30 | 0/30 |
| TinyMog（作者推荐 / GUI 默认） | 0/30 | 0/30 | 0/30 | **11/30** | 0/30 | 0/30 | 0/30 |

结论（这是"首选给谁"的决定性证据）：

- **首选 = `YoloV8Face`**：对输入尺度几乎免疫（320–1280 全档 30/30），框一致性 0.95、小脸极限 32px、43 例 1.3s——**不需要为素材调参**。 ⚠️ **该结论只成立于"已对齐头像"素材；真实片源基准（§8.7）已把通用首选改为 `YoloV11nFace`。**

  它的真实优势只有：**快（0.5s vs Yolo 的 1.3s）与体积小（2.7MB vs 11.7MB）**。
- 作者推荐 TinyMog、且它是 GUI 默认——那是针对"整帧视频"这一默认场景，与"素材多变、要一个不折腾的默认"的诉求并不一致。

   MogFace 那种"大模型 = 更高精度"（0.93、140s）反而是**又慢又不如 Yolo**。

### 8.6 TinyMog 该不该做首选 + 两个环节别混淆

**结论：TinyMog 不必作为通用首选**，实测四条理由（都在上文）：
1. 最快不是它（BlazeFace 0.2s vs 0.5s）；
2. 0.5s 档最准不是它（RetinaFace_500m 0.97 vs 0.94）；
3. 已裁大脸漏检**不可修**（唯一 640 一档 11/30，其余 input_size 全 0/30）；
4. 它自带的 5 点 kps 也不如 RetinaFace/DamoFD 准（见下表）。
它不可替代的优势只有：**体积最小（2.7MB ≈ Yolo 的 1/4）**、0.5s 速度、以及作者面向"整帧视频"的推荐。
→ 定位为**极省资源档**保留，不作为通用默认；通用默认给 `YoloV11nFace`（§8.7 修正后）。

#### 检测器自带的 5 点 kps 准不准（20 张脸裁剪，与大脸比例适中的画面上下文）

| 检测器 | 有 5 点 kps | RMS / 双眼间距 | 逐点偏差 %IOD（左眼/右眼/鼻/左嘴角/右嘴角） |
|---|---|---|---|
| RetinaFace_10g（= DamoFD） | ✅ | **0.0193** | 1.6 / 0.6 / 2.8 / 1.7 / 1.9 |
| TinyMog | ✅ | 0.0441 | 3.0 / 2.9 / 4.9 / 3.0 / 6.6 |
| YoloV8Face / BlazeFace | ❌ 无 kps 接口 | — | — |

- 这 5 点**不是 68 点标记点**，它只用于 `--kps-align`（检测器 5 点预旋转歪脸）；Extractor 里**仅对 DamoFD / RetinaFace / TinyMog 生效**，Yolo 系与 BlazeFace 无此接口。
- 参照系是 2d106 的 68 点派生的标准 5 点（非人工真值），n=20、命中 6 张（大脸比例所限）；差距 2.3× 足够明显。
- **所以"TinyMog 是被推荐因为标记准"不成立**：作者 tooltip 的"轻量高精度"说的是**检测框**，而且它的自带关键点在同一档里偏差最大。

#### 顺带实锤：DamoFD 就是 RetinaFace_10g

`modelhub\onnx\DamoFD\DamoFD.onnx` 与 `modelhub\onnx\RetinaFace\det_10g.onnx` 的 **MD5 完全相同**
（4C10EEF5C9E168357A16FDD580FA8371），所以两者耗时（2.9s）、命中模式（已裁大脸 10/30）、kps 数字（0.0193）逐项一致。
**"远景三选一"实际是二选一：`RetinaFace_10g`（= DamoFD）或 `TinyMog`。**

| **PFLD** | 0.0415 | 0.0509 | 0.0723 | 0.0549 | **1 ms** | **0.40 / 0.88 / 1.10（最稳）** |
| insightface-2d106det | 0.0445 | 0.0596 | 0.0725 | 0.0589 | 5–12 ms | 0.34 / 1.66 / 0.87 |
| MobileFaceNet | 0.0799 | 0.1248 | 0.1241 | 0.1096 | 1 ms | 1.37 / 1.22 / 1.61 |
| Google-mediapipe | 0.0931 | 0.1016 | 0.1885 | 0.1277 | 2 ms | 1.56 / 1.41 / 0.70 |
| OpenSeeFace | 0.1631 | 0.1685 | 0.1792 | 0.1703 | 5 ms | 0.45 / 2.33 / 2.90 |

**结论**

1. 真实片源上 **3d68（修好后）/ 3DFAN-4 / 2DFAN-4 / PFLD 四个基本并列**（0.050–0.055），2d106 紧随（0.059）。
   —— 说明"默认 2d106"依然站得住（它不需要补丁、速度 5–12ms、取景也稳），但**没有精度优势**。
2. **PFLD 是性价比之王**：1 ms/帧（比 FAN 快约 140×）+ 残差 0.055 + 取景抖动最小。
   大批量/超长片优先考虑它；原先把它列为 P2，实测可以提为"省算力首选"。
3. **3d68 在真实片源上残差最低（0.050）**，速度（41–113ms）还快于 FAN；代价是仓库只取 x/y 且依赖 §五 的本地三处补丁（升级会覆盖）。
4. **FAN 两兄弟在这段素材上没有任何精度优势**（0.053 / 0.053 与 3d68/PFLD 同级，却慢 140ms）——它们的主场仍是侧脸/大角度（见 §二 侧脸分档表），不要为"通用精度"付 140ms。
5. `OpenSeeFace` 依旧最差（0.170，与 §四 的 logit 解码缺陷一致）；mediapipe / MobileFaceNet 中下（0.11–0.13）。
6. **caveat**：共识残差衡量的是"与主流一致"，不是绝对精度——自带一套规范模板的标记点（如 mediapipe）天然吃亏；
   多个标记点一致时才说明该位置可信。
